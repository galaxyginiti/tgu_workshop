# Занятие 5. Построение и обучение модели

Проект «Прогнозирование оттока абонентов». Начало этапа: **31 октября 2026**. Сдача: **к началу занятия 7 ноября 2026**.

## Цель

Обучить два согласованных метода, сравнить небольшой набор конфигураций с базовым правилом, выбрать кандидата по validation и сохранить его для следующего этапа. Используйте только ранее выданные данные и собственные признаки четвёртого этапа.

## Шаг 1. Проверка входа

Загрузите `features.csv`, `labels.csv` и `split.csv`. Объедините их по `(customer_id, snapshot_at)`. Позиционное присваивание меток из другой таблицы без проверки порядка недопустимо.

Проверьте уникальность и совпадение множеств ключей, известность меток train/validation, типы и список X. Ключи, будущая метка, конец горизонта и поля аудита не должны попадать в модель автоматически. Убедитесь, что строки после объединения не потеряны и в каждом снимке сохранена согласованная активная база.

Разбиение сохраняется с четвёртого этапа. В стандартном варианте даты расчёта: train 01.12.2025–01.07.2026, validation 01.08.2026, test 01.09.2026. При другом уже согласованном варианте явно запишите даты. Будущие интервалы train должны полностью наблюдаться к началу validation. Самих более ранних дат T для этого недостаточно.

Не пересоздавайте разбиение случайным перемешиванием. Если второй класс отсутствует в train, модель бинарного ухода на нём не обучается: сначала проверьте подготовку и период.

## Шаг 2. Baseline на тех же данных

Воспроизведите сортировку по доступному долгу предыдущего месяца. Равенства — по ID. Неизвестный долг размещайте после известных либо используйте ранее согласованное явно описанное правило. Это способ ранжирования, а не восстановление неизвестного значения.

Для каждой даты T вычислите K от полной активной базы. На **train и validation** сохраните N, K, число ушедших, число найденных, Recall@K и Precision@K. Если положительных исходов нет, Recall неизвестен; при K=0 Precision неизвестна. Такие значения не подменяйте нулями. Укажите правило усреднения по датам.

Baseline не входит в число двух обучаемых методов. Сравнение train одного подхода с validation другого не отвечает на вопрос о преимуществе.

## Шаг 3. Два обучаемых метода

Используйте два кандидата, выбранных на этапе 4. При замене метода объясните причину в журнале. Примеры в комплекте показывают логистическую регрессию и HistGradientBoostingClassifier; конкретная библиотека не является обязательной, если соблюдены условия проекта.

Для каждого опыта создавайте новый Pipeline или эквивалентный воспроизводимый процесс. Подготовку и классификатор обучайте только на train. На validation применяйте уже обученную подготовку. Не передавайте в fit отложенные метки и не заполняйте пропуски по всем периодам.

Проверьте поведение выбранной реализации: необходимость кодирования, допустимость пропусков, масштабирование, настройки остановки. Шаблон бустинга отключает автоматическую раннюю остановку со случайной внутренней подвыборкой. Если используете early stopping, подберите для него временно корректный внутренний период из train; не используйте test и не меняйте внешний порядок оценки.

Веса классов или изменение баланса допускаются как отдельный обоснованный опыт. Преобразования с обучением и ресемплинг выполняются только в обучающей части, а при временных фолдах — внутри каждого фолда. Стандартный комплект не требует SMOTE или другого ресемплинга.

## Шаг 4. Ограниченный план экспериментов

Выполните **3–6 осмысленных конфигураций суммарно по двум методам, максимум 8**. Например, две силы регуляризации и два значения сложности бустинга. Нельзя представлять разные seed одного и того же метода как два метода.

До сравнения запишите изменяемые параметры и критерий выбора. Для первого сопоставимого эксперимента сохраняйте один набор X и одно разбиение. При последующей замене признаков создайте новую версию и зафиксируйте изменение; не выбирайте её по тестовым исходам.

Для каждого опыта сохраните ID, метод, параметры, seed, версию признаков, train/validation-метрики, время обучения и статус запуска. Ошибка обучения или предупреждение о несходимости не должны исчезать из журнала: опишите причину и исправление. Измеряйте время на своей машине, не сравнивайте его напрямую с чужим оборудованием.

Обширный перебор не требуется. Многократная подгонка по одному месяцу validation снижает убедительность итоговой оценки. Для дополнительной проверки можно заранее согласовать несколько временных фолдов внутри train с повторным fit всей подготовки в каждом фолде.

## Шаг 5. Оценки риска и метрики кампании

Для каждой модели получите непрерывный score. Если используете `predict_proba`, убедитесь, какой столбец относится к классу ухода 1. Score применяется для ранжирования; точность вероятностей как вероятностей отдельно проверяется на следующих этапах.

По каждой T сортируйте всю активную базу по score по убыванию, при равенстве — по `customer_id` по возрастанию. Выбирайте первые K. Не округляйте score перед ранжированием и не заменяйте top-K фиксированным порогом 0,5.

- Recall@K = найденные будущие ушедшие / все будущие ушедшие.
- Precision@K = найденные будущие ушедшие / K.
- Average Precision (AP) — дополнительная характеристика ранжирования. В примере используется `average_precision_score`. Это определённый способ суммирования precision-recall кривой, он не тождествен трапецеидальной PR-AUC. Если используете PR-AUC, явно укажите способ расчёта.

Покажите метрики отдельно на train и validation, а также числители и знаменатели на каждой T. При нескольких validation-датах заранее выберите способ агрегирования; основной пример использует macro Recall@K по датам. Pooled Recall по суммарным исходам укажите отдельно, если приводите его.

Accuracy не является основным критерием выбора в редком оттоке. Большой разрыв train/validation и рост качества только на train могут указывать на переобучение или изменение данных; это нужно обсудить, а не скрыть.

## Шаг 6. Выбор и фиксация кандидата

Используйте заранее записанное правило. Пример: максимальный validation macro Recall@K; при равенстве — максимальный validation AP; при полном равенстве — первый опыт в заранее заданном порядке. Можно принять более простой кандидат при равенстве, если это правило зафиксировано до выбора.

Сравните кандидата с baseline на той же validation. Зафиксируйте число дополнительных найденных уходов. Если baseline лучше, это допустимый результат корректного этапа: модель не объявляется готовой к внедрению. Выбранный обученный кандидат сохраняется для следующей проверки, а baseline остаётся рабочей альтернативой.

**Test на этом занятии не оценивайте.** Не стройте по нему ошибки, importance и графики для выбора настроек. После выбора не переобучайте на train+validation: сохраните именно ту версию, которую сравнили. Итоговая оценка, интерпретация и дальнейший протокол переобучения относятся к шестому этапу.

## Шаг 7. Сохранение и воспроизводимость

Сохраните Pipeline целиком: преобразование и классификатор. Приложите имена/порядок входных столбцов, параметры, seed, версии библиотек и идентификатор версии данных/признаков. Сохранение одного классификатора без обученной подготовки недостаточно.

В новом процессе загрузите собственный объект и получите validation-оценки без fit. Сравните ключи, численные score с разумным допуском, порядок top-K и метрики. В комплекте есть пример `check_saved_model.py`; он ожидает структуру bundle из стартового ноутбука. Сохраните необходимые пользовательские Python-модули рядом с кодом загрузки.

Предусмотрите единый запуск обучения и отдельную команду проверки сохранённого кандидата. Исходные таблицы четвёртого этапа не изменяйте. Выходные прогнозы и метрики являются результатами обработки прежних данных.

## Комплект сдачи к 7 ноября

1. Код и конфигурация запуска, версия признаков, зависимости и команды обучения/загрузки.
2. Журнал 3–6 конфигураций, результаты двух обучаемых методов и baseline отдельно на train/validation.
3. Расчётные таблицы по T: N, K, ушедшие, найденные, Recall@K, Precision@K и дополнительная метрика, если используется.
4. Validation-прогнозы выбранного кандидата: ключи, score, rank, признак попадания в top-K; истинная метка может находиться отдельно.
5. Сохранённый Pipeline, схема его входов и проверка загрузки в новом процессе без fit.
6. Отчёт на 2–3 страницы: выбор кандидата, сравнение с baseline, разрыв train/validation, ограничения и план шестого этапа.
7. Краткое описание вклада участников и ссылка на версию репозитория.

Ориентир самостоятельной работы: **6–8 часов на команду при готовом четвёртом этапе**. Не требуется сложная инфраструктура трекинга: достаточно файлов параметров, таблицы результатов и сохранённой версии кода.

## Критерии приёмки

| Критерий | Что демонстрирует команда |
|---|---|
| Вход | Ключи, метки, список X и временные границы проверены |
| Обучение | Два метода действительно обучены на train; подготовка не использует validation/test |
| Сравнение | Baseline и модели используют одну базу, K и метрики |
| Эксперименты | Небольшой осмысленный план, полный журнал и правило выбора |
| Выводы | Переобучение и ограниченность validation учтены, преимущество не преувеличено |
| Воспроизводимость | Сохранённый Pipeline выдаёт те же validation-результаты без fit |

Превышение baseline само по себе не заменяет корректность этапа. Корректный отрицательный результат с честным анализом не считается невыполнением задания.

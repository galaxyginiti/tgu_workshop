# Прогнозирование оттока абонентов «СвязьРегион» — решение команды

Командный проект IT-Практикума 5 «Искусственный интеллект и большие данные» (осень 2026). Задача: на первое число каждого месяца оценить риск расторжения договора для активных абонентов и выбрать для удерживающей кампании не более 10% базы.

Исходные материалы курса лежат в корне репозитория (`1_introduction/` … `4_features/`) и **не изменяются**. Решение команды — в этой папке.

## Быстрый запуск

```bash
python -m venv .venv
.venv\Scripts\activate            # Linux/macOS: source .venv/bin/activate
pip install -r solution/requirements.txt
python solution/run_all.py        # этапы 2 → 3 → 4, ~15 с
```

Запуск выполняется из корня репозитория. Отдельный этап: `python solution/run_all.py --stage 3`, но этапам 3–4 нужны результаты этапа 2.

После запуска:

- все таблицы, рисунки и проверки лежат в `solution/stage*/output/`;
- `solution/output_manifest.csv` содержит sha256 каждого результата. Два запуска подряд дают идентичный манифест — так проверяется воспроизводимость;
- код возврата ≠ 0, если хотя бы одна проверка не пройдена.

## Этапы и результаты

| Этап | Дедлайн | Документ | Ключевые результаты |
|---|---|---|---|
| 1. Инициация | 10.10 | [Устав проекта](stage1_charter/Устав_проекта.md) | Отток = termination; T = 1-е число 00:00 МСК; горизонт — календарный месяц; база `activation < T`, `termination ≥ T`; Recall@10% — основная метрика |
| 2. Подготовка данных | 17.10 | [Отчёт о качестве](stage2_preparation/Отчёт_о_качестве.md) | 5 чистых таблиц, `customer_month` 24 098 строк (= биллинг), карантин 180 записей, журнал из 20 решений, 21 проверка |
| 3. EDA | 24.10 | [Отчёт EDA](stage3_eda/Отчёт_EDA.md) | `eda_sample` 15 696 строк на 8 датах; долг > 0 → 7,5% оттока против 1,4%; 6 рисунков с расчётными таблицами; 4 гипотезы; 17 проверок |
| 4. Признаки и метод | 31.10 | [План моделирования](stage4_features/План_моделирования.md) | 34 признака (32 в X → 58 столбцов), `features` / `labels` / `split` / `feature_audit`; baseline по долгу Recall@K = 39,8% (случайный ≈ 10%); 28 проверок |

Каждый этап сдаётся отдельным тегом (`stage-1` … `stage-4`) в этом репозитории.

## Главные правила, которые соблюдаются во всём коде

1. **Время.** Все моменты приведены к Москве (+03:00). Признак на T строится только из записей с моментом доступности ≤ T: `available_at` биллинга, обращения, цифрового отчёта, `report_available_at` сети.
2. **Метка отдельно.** Будущие расторжения используются только для `churn_target`, в признаки не попадают. Горизонт за пределами журнала (01.10.2026) даёт неизвестную метку, а не 0.
3. **Неизвестное ≠ 0.** Пропуски трафика, неопубликованные отчёты, ноль попыток оплаты остаются пропусками. Импутация — только внутри `Pipeline` и только на train.
4. **Никого не удаляем.** Абоненты с пропусками и короткой историей остаются в базе, полнота хранится отдельными признаками.
5. **Отложенные даты.** Validation (01.08.2026) и test (01.09.2026) не используются для выбора гипотез и признаков.

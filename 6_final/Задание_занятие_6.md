# Занятие 6. Проверяем результат и готовим защиту

Проект «Прогнозирование оттока абонентов». Объединённые этапы 6 и 7.

**Выдача — 7 ноября. Полный комплект — к началу занятия 14 ноября.** На завершение — одна неделя. Новые исходные данные не выдаются.

## Что сдаёт команда

Всего **три результата**:

1. **Проект:** ссылка на репозиторий или ZIP с рабочим кодом, сохранённой моделью, зависимостями и результатами расчёта.
2. **Короткий README внутри проекта:** протокол, порядок запуска, таблица качества, небольшой анализ и вывод.
3. **Готовая презентация на 8–12 слайдов:** PDF **или** PPTX. Достаточно одного варианта для показа.

README заменяет отдельный итоговый отчёт, техническую документацию и пользовательскую инструкцию. Отдельные отчёт и чек-лист сдавать не нужно. Протокол — пять строк внутри README.

Ориентир работы после занятия — **4–6 часов на команду при завершённом этапе 5**. Доработка незавершённого обучения потребует дополнительного времени.

## С чего начать

Используйте свои `features.csv`, `labels.csv`, `split.csv` этапа 4 и выбранную по validation, сохранённую модель этапа 5. Сохраняйте согласованные ранее правила метки, активной базы и разбиения. Если этап 5 не закончен, сначала выберите модель по validation.

Пересобирать все исходные данные заново не требуется: запуск может начинаться от подготовленных признаков этапа 4. Укажите это в README.

## Шаг 1. Заполните короткий протокол

Перенесите пять строк из `Протокол_итоговой_проверки.md` в README: модель, test и горизонт, правило сравнения, метрики, история использования test. Это краткая фиксация уже принятых решений.

Для стандартного плана test — снимок на 1 сентября 2026; метка — расторжение в календарном сентябре, до 1 октября. Если ранее согласовали другой горизонт, используйте его. Будущий исход должен быть известен; неизвестный исход нельзя заменять нулём.

## Шаг 2. Сравните сохранённую модель и baseline

Загрузите сохранённый Pipeline и рассчитайте score на test **без fit**. Не переобучайте его на train+validation перед этой проверкой и не выбирайте нового победителя по test.

Сопоставляйте признаки и метки по `(customer_id, snapshot_at)`. Используйте всю активную базу, сохраняя строки с пропусками по правилам этапа 5.

Модель и baseline сравниваются на одной базе при **K=floor(0,10 × N_active)**. Равные score разрешаются по ID по возрастанию. Baseline — долг прошлого месяца по убыванию; правило неизвестного долга сохраните из этапа 5. Порог 0,5 вместо top-K не используется.

Заполните одну таблицу в README:

| Период | Подход | N / K | Найдено / ушли | Recall@K | Precision@K |
|---|---|---|---|---|---|
| Validation | Baseline | […] | […] | […] | […] |
| Validation | Модель | […] | […] | […] | […] |
| Test | Baseline | […] | […] | […] | […] |
| Test | Модель | […] | […] | […] | […] |

- **Recall@K** = найденные уходы / все уходы в проверяемой базе.
- **Precision@K** = найденные уходы / K контактов.
- Если знаменатель равен нулю, обозначьте метрику «не определена».

Результаты validation перенесите из этапа 5; заново проводить эксперименты не нужно. При нескольких датах добавьте строки по датам. AP/PR-AUC можно оставить, если уже считали; для сдачи они не обязательны.

В 1–2 предложениях сравните validation и test: сохранилось ли преимущество над baseline, сколько уходов найдено при одном K. Один test-месяц не доказывает устойчивость на будущих периодах.

Сохраните таблицу метрик и test-списки модели и baseline: ключи, score, rank, selected. Их можно оставить в формате уже работающего кода.

## Шаг 3. Сделайте один небольшой разбор и объясните признаки

Выберите **один** вариант анализа:

- **Два случая ошибки:** пропущенный уход (FN) и выбранный, но не ушедший в горизонте абонент (FP). Для каждого достаточно ID, score/rank, исхода, 2–3 признаков и короткого комментария. Если такой группы нет, укажите это и разберите доступный случай.
- **Одно сегментное сравнение:** например, тарифы или стаж. Покажите размер групп, число уходов и найденных уходов. Отбор берите из **общего top-K**, заново выбирать 10% внутри каждой группы не нужно. При 100% из одного события пишите «1 из 1», чтобы был виден масштаб результата.

Затем объясните смысл **трёх признаков**: что измеряет каждый, почему может быть связан с уходом и на что опирается объяснение. Достаточно выводов EDA из этапа 3 или уже полученных коэффициентов/важностей. Связь в EDA не называйте доказанной важностью для модели или причиной ухода.

Новый расчёт permutation importance, SHAP, стресс-тесты, доверительные интервалы и второй сегментный разбор **не обязательны**. Если это уже сделано, можно использовать готовый результат.

## Шаг 4. Оформите README и проверьте запуск

В `Шаблон_README.md` уже собраны нужные разделы. Заполните пути к прежним данным, зависимости, точную команду или короткую последовательность запуска и ожидаемые выходы. Объясните, что означает список контактов. Существующую структуру проекта можно сохранить; API, Docker и новый Git-тег не требуются.

Оставляем **три проверки**, по возможности — имеющимся кодом:

1. **Сопоставимость:** ключи и активная база сохранены; у модели и baseline одинаковые N и K.
2. **Корректность оценки:** загружена выбранная модель, подготовка и модель не обучаются и не подбираются на test.
3. **Повторный запуск:** повторная загрузка той же модели на тех же входах даёт тот же список контактов и те же метрики.

Повтор может выполнить любой участник, в том числе автор, в текущем рабочем окружении. В README достаточно одной строки с результатом; отдельный акт, журнал и запуск в новом окружении не требуются. Такой повтор подтверждает воспроизводимость расчёта, но не устойчивость качества на новых данных.

## Шаг 5. Подготовьте вывод и презентацию

Вывод для заказчика: **результат с числами → два главных ограничения → рекомендуемое действие**. Если модель уступила baseline, честно напишите это: победа модели не является условием зачёта. Прогноз ухода не показывает, сколько клиентов удержит контакт; денежный эффект без исходных данных не оцениваем.

`Шаблон_защиты.md` содержит восемь базовых слайдов: задача; данные; подготовка и признаки; модель и правило сравнения; качество; объяснение результата; запуск и ограничения; рекомендация. При необходимости можно добавить до четырёх слайдов. **Регламент: 12 минут выступление + 3 минуты вопросы — всего 15 минут на команду.** Числа должны совпадать с README; каждый участник должен понимать общий вывод.

**14 ноября сдаётся законченный комплект, а не черновик.** Если защита по прежнему расписанию остаётся на 21 ноября, это не переносит срок готовности с 14 ноября.
